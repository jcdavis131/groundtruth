# Changelog

The public MCP server and its published schema, newest first. `SERVER_VERSION` (`lib/mcp/server.ts`) is the server string a client reads from `initialize` and `GET /api/mcp`; it is not the `world/N` schema version, which is `schemaVersion` on a `world_context` reply. `lib/mcp/server.lock.json` holds a hash of what `tools/list` says for each version here, and `lib/mcp/server.test.ts` fails when `tools/list` or `world_context`'s `outputSchema` changes without a new version and a dated heading below. The rules are in `docs/MCP.md`, "Versioning promise": additive within `world/N`, and a removed or renamed tool is announced under "Deprecated" here at least 30 days before it goes.

## 0.7.0 - 2026-10-21

A `world_context` item says what date its publisher puts on the data, where its route states one, and `stale` compares that date, so it can fire on live data. Three byte trims from the 0.6.0 review. Additive within `world/2`.

- Published surface (the only part the lock sees): in `world_context`'s `outputSchema`, an item gains one optional property, `publishedAt`: a date or a UTC datetime, as the route wrote it, or null. Unlike `snapshotAt` it has no rule beside it: a null `publishedAt` needs no `note` on the item, because the reason is the same for every item and the reply's own `note` says it once. No property was removed or retyped, no `required` was relaxed, no `const` or enum value was dropped: `server.schema-compat.test.ts` passes against the unchanged `world/2` baseline, and the baseline file is not edited. `cadence` still allows null in the schema, so a 0.6.0 reply validates, but 0.7.0 no longer sends it. No tool description, input schema or annotation changed, so only `world_context`'s hash and the whole-list hash moved in the lock.
- On a reply, `publishedAt` is read from the one field a route states it in, and from nowhere else (a whitelist by source in `PUBLISHED`, `lib/mcp/world.ts`). Never the `retrievedAt`, never the reply's time, never today. Read on 2026-10-21 from the live routes (each answered HTTP 200 but the dams call, which timed out upstream and was read from the route's code), what each source states:
  - `hifld-hospitals`: the infra route's `dataLastEdited` (the same date as its provenance period "data last edited 2026-04-22"). The route types it as a constant (`HOSPITALS_DATA_EDIT`, `lib/infra/hospitals.ts`); it does not read the layer on each call.
  - `cms-provider-data`: the infra route's provenance period "dataset modified 2026-07-22", matched as that exact sentence.
  - `usdm`: the hazards route's `droughtNow.mapDate` (2026-10-13 at the time), the date the Drought Monitor puts on its weekly map. The Monitor releases it two days after that Tuesday.
  - Null, because the route states no date of the publisher's own: `bls-qcew`, `zillow-zhvi` and `zillow-zori` (the screen route's period, "2026 Q1" and "2026-09-30", is the period the value describes, not when it was released), `sec-edgar` (the companies route's `releasedAt` is the day eye pulled EDGAR, which is `snapshotAt` already; SEC states no date), `fema-nri` (its label "December 2025" names the release), `cdc-svi` (period "ACS 2018-2022 (SVI 2022)"), `fema-openfema`, `usace-nid` (its provenance says each record carries its own update date), `epa-cws-boundaries`, `epa-ucmr5-pat`, `nws-api`, `usgs-earthquakes`, the fabric's `census-tigerweb`, `usgs-epqs`, `fema-nfhl`, `usgs-wbd` and `epa-ecoregions`, eye's own catalogue, and the "next scheduled release" items (a window worked out from the calendar's rules).
- Stale: the age compared with the cadence window is now the item's `publishedAt` when it has one, else its `snapshotAt`, and the reason says which ("its own date for this data is 2026-10-13" or "eye serves a snapshot from ..."). The window table (`STALE_AFTER_DAYS`) is unchanged. A live or cached route's `snapshotAt` is its fetch time and cannot reach a window of 10 days or more; a publisher's own date can. Of the sources `world_context` cites that have a calendar entry (BLS QCEW, Zillow, the Drought Monitor), only the Drought Monitor states one, so `stale` can now fire on production for it alone, when its map is dated more than 10 days ago. That window is counted from the map's Tuesday, while the Monitor releases on the Thursday after and the hazards route caches a county's reading for a day: for up to half a day after each release a county read just before it can show `stale` although the Monitor is current. The brief for this change kept the table, so the row is unchanged; a longer weekly window for a map-date basis is a decision for Cam. HIFLD and CMS state a date and have no calendar entry, so they are never stale.
- Byte trims: the stale sentence is written once, on the `missing` entry, and its two coverage basis lines (the topic's and the reply's) are the code and the source ("bls-qcew freshness") instead of the sentence again. `cadence` is left out where the calendar has no entry instead of sent as null (15 bytes an item, and absence says the same). The release-window items' "no snapshot date" clause is "a computed window" instead of a sentence.
- Stdio: `scripts/mcp-stdio.mjs` now passes the release calendar to `createServer`, as `app/api/mcp/route.ts` does, so over stdio an item has a `cadence` and a stale one is flagged. `lib/releases/calendar.ts` has one import, a type, which `tsc` cannot resolve when `lib/mcp` compiles alone, so the script transpiles that one file without type-checking (TypeScript's `transpileModule` drops a type-only import) next to the `tsc` emit.
- Not in this change: `data/cadence.json` (the data pipeline's table, keyed by collection) is still a different table that `lib/mcp` cannot read; the recorded fixtures are not re-recorded (the recorder drops `dataLastEdited` and period, so they show the Drought Monitor's date only); the HIFLD and CMS dates are typed in the repo, not read from the publishers on each call.
- Version number: 0.6.0 to 0.7.0, a minor bump for an additive change. `public/openapi.json` carries the same number (`server.test.ts` holds the two together).
- Recorded in `lib/mcp/server.lock.json` as the fourth entry; the 0.4.0, 0.5.0 and 0.6.0 entries are untouched.

## 0.6.0 - 2026-10-21

A `world_context` item says when the data behind it was fixed and how often its publisher releases, and a source whose snapshot is older than that is labelled `stale`. Additive within `world/2`.

- Published surface (the only part the lock sees): in `world_context`'s `outputSchema`, an item gains two optional properties. `snapshotAt` is a date or a UTC datetime, as the route or the bundle wrote it, or null. `cadence` is `{ kind, precision, source }` (the release calendar's cadence word, whether its date is official or approximate, and the calendar entry's id) or null. One rule is added and it applies only to the new property: an item whose `snapshotAt` is null carries a `note`, the way an item whose `value` is null already must. The absence code list gains `stale` (action `none`, not retryable, no FHIR code), so `code` in a `missing` entry or a coverage line can now be `stale`. No property was removed or retyped, no `required` was relaxed, no `const` or enum value was dropped: `server.schema-compat.test.ts` passes against the unchanged `world/2` baseline, and the baseline file is not edited (it is "committed once and never edited"; 0.5.0 left it alone too). Only `world_context`'s hash and the whole-list hash moved in the lock; no tool description, input schema or annotation changed.
- On a reply: `snapshotAt` is the `retrievedAt` the item's route sent, or for a bundle its own recorded date, as written: the SEC bundle's `pulled` (a bare day, not padded to a time) and, on `place.point`, the county table's `pulled`. It is null, with the reason ending the item's note ("no snapshot date: ..."), for eye's own catalogue, for the CMS-to-HIFLD bundle (its meta records no build date; the route types one in its own code, which is not the bundle's record), for the SEC fixture (`pulled: null`), for the "next scheduled release" items (a window worked out from the calendar's rules on each call) and for a source whose route sent no `retrievedAt` (never the reply's own time, which `retrievedAt` falls back to). `cadence` is the release calendar's entry for the item's source: BLS QCEW (quarterly), Zillow (monthly) and the Drought Monitor (weekly, official) have one; FEMA, CDC, Census, EPA, NWS, USGS, HIFLD, USACE and SEC do not, and say null. A server given no calendar sends no `cadence` and flags nothing.
- Stale: a snapshot older than the window for its cadence (annual 366 days, quarterly 100, monthly 35, weekly 10, daily 2; continuous never) puts one `{ what: "<sourceId> freshness", code: "stale", action: "none" }` entry in its topic's `missing`, once per source, with the publisher, the cadence and the date in the reason, and a `stale` line in that topic's coverage basis. The items stay: stale is a label and not a withholding. The table is `STALE_AFTER_DAYS` in `lib/mcp/world.ts`. `none` and no FHIR code because the item is still shown: HL7's data-absent-reason set (`temp-unknown` included) says why a value is missing, and a stale item keeps its value. Over the twelve recorded replies, with the calendar injected, none is stale on the day it was recorded; a year later 33 entries are: the Drought Monitor in 11 replies, BLS QCEW in 10, Zillow home value in 7 and Zillow rent in 5.
- Cost in bytes: about 40 bytes an item for `snapshotAt`, 15 for a null `cadence`, 80 for a calendar one, and about 540 for the sentence in the reply's `note`. The Austin default reply goes from 34,462 to 38,449 bytes and Collegeville's from 34,069 to 37,944 against the 40,000 cap; all twelve recorded replies stay whole, with 1,500 bytes left on the largest. A stale source adds about 600 bytes (its entry, and its line in the topic's and in the reply's coverage basis), so a reply that is both near the cap and stale can lose items to `cut_by_byte_cap`, which says so. Under today's caching no live source can reach its window (the screen route stamps `retrievedAt` at assembly, hours behind at most, against windows of 10 days and up), so on production `stale` fires only on a replayed or bundled old snapshot; this change ships the field and the tested mechanism, not a live staleness signal yet.
- Not in this change: the publisher's own last-edit date (the infra route states one for HIFLD hospitals and CMS, in `meta.dataLastEdited` and in the provenance `period`; nothing reads them yet, and most routes state none), the data pipeline's collection table `data/cadence.json` (a different table, keyed by collection; `lib/mcp` cannot read it), and the stdio server (`scripts/mcp-stdio.mjs` passes no calendar, so over stdio an item has no `cadence` and nothing is flagged).
- Version number: 0.5.0 to 0.6.0, a minor bump for an additive change. `public/openapi.json` carries the same number (`server.test.ts` holds the two together).
- Recorded in `lib/mcp/server.lock.json` as the third entry; the 0.4.0 and 0.5.0 entries are untouched.

## 0.5.0 - 2026-10-20

Counts that `world_context` computes are labelled estimates, and say what they were computed from. Additive within `world/2`.

- Published surface (the only part the lock sees): in `world_context`'s `outputSchema`, an item's `kind` gains the value `"estimate"` (it was `"about-eye"` only), and a new optional property `inputs` is added: a non-empty list of `{ sourceId, route, upstreamRecordUrl?, retrievedAt }`, the source a count was computed from, the eye route whose reply held the rows, the publisher's own URL for what the route read, and that source's own retrieval time. Three rules are added: a `kind` of `"estimate"` requires `inputs`, `inputs` appear only on an `"estimate"`, and an item cited to eye's own catalogue stays `"about-eye"` (so widening `kind` loosens nothing). No property was removed or retyped, no `required` was relaxed, no `const` or enum value was dropped: `server.schema-compat.test.ts` passes against the unchanged `world/2` baseline. Only `world_context`'s hash and the whole-list hash moved in the lock; no other tool's description, input schema or annotations changed.
- On a reply: every count `world_context` builds from a route's list is `kind: "estimate"` with one input: Severe or Extreme NWS alerts touching the box, M4.5+ earthquakes touching the box, `hospitals found` and `dams found` (0) and the SEC bundle's 0. 33 of the 313 valued lines in the twelve recorded replies. The items keep their note ("no record-level URL: a count ...") and still have no `upstreamRecordUrl`. The reply's `note` says what an estimate is. A reader that ignores `kind` and `inputs` reads every older reply as before.
- Outside the lock (these tools publish no schema): six provenance entries that were labelled `published` and describe values computed here are `estimate` with `inputs`. `county_history`: FEMA declarations per year, SPC tornadoes per county per year, NCEI storm reports per year per type. `movers` for Zillow, BTS border and BTS ports: `changeAbs` and `changePct`, with `rowIdsAt` `data.up, data.down`. `citation()` now ends such a record with "estimate computed by Embedding Atlas: <method>". BLS QCEW movers stay `published`.
- Version number: 0.4.0 to 0.5.0, a minor bump for an additive change. `public/openapi.json` carries the same number (`server.test.ts` holds the two together).
- Recorded in `lib/mcp/server.lock.json` as the second entry; the 0.4.0 entry is untouched.

## 0.4.0 - 2026-10-20

World/2 and the surfacing contract, recorded as one server version. The first entry the version lock holds.

- Version number: 0.1.0 to 0.4.0 in one step. `public/openapi.json` already said 0.3.0 and now carries the same number as the server, so the larger was kept and no published number goes backwards. 0.2.0 and 0.3.0 were never server versions.
- Surfacing contract (#65, merged 2026-10-20): the server's `instructions` (1,017 characters), the `_meta` alwaysLoad flag on `world_context` alone, every tool description at most 3,800 characters.
- Typed absence and the `world/2` outputSchema (#69, merged 2026-10-20): every `missing[]` entry and `coverageStatus` basis line of a `world_context` reply carries a code from a closed list with an action; `world_context` publishes its `outputSchema` in `tools/list` and `GET /api/mcp`; every reply is checked against it before it is sent. `schemaVersion` `"world/2"` is a new key on the reply. It is additive within `world/2` and is not a schema version bump.
- This change (W3P): the version lock, the check of the published schema against the committed `world/2` baseline (`lib/mcp/server.world-2.schema.json`), `public/openapi.json` carrying `SERVER_VERSION` and https://www.arxiviq.com as its first server. No tool, description or schema changed in it. Alongside it, nine sources `world_context` relays now carry a `licenseId`, each with the publisher's own page and the day it was read.
- Before the lock: 0.1.0 had no recorded hashes, so what changed inside it cannot be rebuilt from this file.
